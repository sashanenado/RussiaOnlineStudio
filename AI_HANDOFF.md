## 2. Жёсткие требования пользователя — не нарушать

1. **Поставка двумя EXE:** Studio и Overlay/Helper. Сохранять этот формат; не объединять всё в один EXE без прямого согласования.
2. **Тёмная тема:** это предпочтение пользователя для приложения.
3. **Автоматическая связь библиотеки и Overlay:** статьи УК, КоАП, ПК и другие поддерживаемые категории должны попадать в соответствующие панели Overlay автоматически. Пользователь не должен вручную копировать текст из библиотеки в Overlay.
4. **Живая синхронизация:** изменение статьи или панели в Studio должно сохраняться и отражаться в Overlay автоматически, без ручного перезапуска/копирования.
5. **Сохранность данных:** не ломать и не терять существующие базы, пользовательские статьи, форматирование, заметки, теги, избранное, профили, настройки и координаты окон. Перед изменениями схемы/миграциями предусматривать безопасную совместимость и резервирование.
6. **Профили:** поддерживать отдельные профили (main / deputy / personal) и корректное сохранение/восстановление их данных.
7. **Overlay:** окна должны оставаться перемещаемыми, сохранять координаты/размеры и корректно отображать выбранные данные.
8. Не делать косметическую перестройку или удалять работающие части ради упрощения. Сначала понять текущую архитектуру, затем исправлять первопричину.
9. Не считать задачу готовой только потому, что код выглядит правильно. Проверять сборку, запуск/поведение доступными средствами и явно фиксировать, что именно проверено.

## 3. Контекст прошлых работ и уже известных проблем

- Ранее в ходе работы были версии v1–v4. В прошлых итерациях уже затрагивались разделение путей данных, сохранение профилей, отдельное окно законов, сохранение координат окон, восстановление исходного `laws_database.json`, автосохранение, FileSystemWatcher/сигналы обновления Overlay, обновление статей и панелей, перетаскивание окон.
- Не откатывать эти функции вслепую. Проверить их в текущей архитектуре и сохранить, если они корректны.
- Пользователь сообщал о конкретном дефекте: добавление статьи через выпадающий список УК работает, но при выборе категории КоАП и добавлении статьи она не добавляется и исчезает из интерфейса. Требование пользователя: не ограничиваться точечным условием, а выстроить правильную общую логику добавления/категоризации, чтобы аналогичные проблемы не повторялись.
- В текущем коде `AddLaw_Click` приоритетно читает `CategoryBox` (фильтр списка), а затем `EditCategory`. Это нужно проверить как потенциальную причину рассинхронизации выбранной категории и категории новой статьи.
- В текущем коде `ApplyLawEditor` меняет категорию статьи, переносит JsonObject между массивами категорий, обновляет `OriginalCategory`. Проверить этот путь вместе с фильтрами, автосохранением и переключением выбранной статьи.
- В `LawRow` уже существует свойство `Tags`; коммит `4f91708` исправляет отсутствующее свойство/загрузку тегов, из-за которых CI на предыдущем commit падал с CS1061.
- Последняя подтверждённая успешная сборка в доступной истории Actions была до ряда последующих изменений. В логах сборки на commit `f519538` проверки JSON баз прошли, но `dotnet publish Studio` упал из-за отсутствующего `LawRow.Tags`. Исправление находится в последующем commit `4f91708`. Обязательно получить свежий CI-результат для текущей ветки, прежде чем считать проблему закрытой.
- В проекте присутствуют Studio и Overlay WPF, база `Data/laws_database.json`, `Data/ExtendedLaws/*.json`, `Data/rules_docs.json`, профили в `Data/Profiles`, встроенный WebView2.
- В исходном архиве есть метаданные ПГО (118 пунктов), но текущая логика приложения сама указывает, что текст самих правил в переданных исходных данных отсутствует. Не выдумывать содержимое ПГО и не подменять его заглушками как настоящим законом.

## 4. Текущая архитектура (по аудиту исходников)

- `src/Studio` — основное WPF-приложение.
- `src/Overlay` — отдельное WPF-приложение Overlay.
- `Data/laws_database.json` — основная база с объектом `Bases`.
- `Data/ExtendedLaws` — расширенные группы статей.
- `Data/Profiles/{main,deputy,personal}` — данные профилей.
- Studio сохраняет JSON через временный файл и атомарное перемещение; есть резервные копии.
- Studio создаёт сигналы ревизий `laws_revision.txt` и `panels_revision.txt` для обновления Overlay.
- В Studio есть автосохранение с таймером 700 мс.
- В Studio встроен WebView2, форум по умолчанию `https://forum.russia.online/`, Ctrl+F обрабатывается через JS bridge и `window.find()`.
- Категории нормализуются методом `NormalizeCategory`; сейчас есть отображаемые названия УК, КоАП, ПК, ПГО, ФЗ о ФСО, О территориях.
- Не предполагать, что наличие метода означает работоспособность функции: проверить XAML bindings, обработчики событий, последовательность событий и взаимодействие процессов.

### Что важно знать о производительности и сохранности

- Расширенный каталог состоит из 24 JSON-файлов общим размером около 3.79 MB. До оптимизации профиль мог сохранять объединённую базу целиком. Частое debounce-автосохранение раньше выполняло всю сериализацию и запись на UI-потоке.
- Для уменьшения задержек файловая часть автосохранения теперь работает через `Task.Run`, а UI передаёт detached snapshot. Записи сериализованы через `SemaphoreSlim`, чтобы синхронное сохранение при смене профиля/закрытии не перезаписало более свежую фоновую запись. При любых дальнейших изменениях этого механизма проверять отсутствие deadlock и порядок версий.
- Это не завершённая оптимизация хранения: профиль всё ещё может содержать копию большого объединённого каталога. Следующий возможный этап — формат profile overrides/delta с tombstones для удалений, но только после аудита уникальности ID во всех исходных категориях и тестов миграции. Не менять формат профилей вслепую.
- В Overlay FileSystemWatcher рассматривается как сигнал к перечитыванию файлов, а не как гарантия доставки каждого события; при Error запрашивается полное перечитывание. Это соответствует документации Microsoft: буфер watcher может переполняться, события могут дублироваться и Error сигнализирует о потере мониторинга.
- Атомарная запись и Flush повышают устойчивость файлов, но не заменяют проверку на реальном Windows-компьютере.

### Непроверенное вручную

CI проверяет компиляцию и структуру файлов, но не выполняет интерактивную проверку пользовательского интерфейса. На реальном Windows-сеансе обязательно проверить: старт обеих программ; добавление и редактирование в УК/КоАП/ПК; смену фильтра и перемещение статьи; быстрый ввод и закрытие во время автосохранения; переключение профилей; рестарт; обновление Overlay; F8–F11 поверх игры; перемещение/размер окон; WebView2 Runtime и авторизацию форума. Не обещать отсутствие любых вылетов до этих проверок.

### Как теперь загружается библиотека

- LoadBundledOrDefault() больше не сливает короткие категории старой корневой базы в активные законы. Она загружает 27 документов из Data/ExtendedLaws по полным заголовкам каталога.

- MergeProfileSafely() переносит на актуальный арбатский документ пользовательские Note, Tags, Favorite, InMemo, если запись сопоставлена по стабильному ID либо однозначному ключу документа/номера/названия.
